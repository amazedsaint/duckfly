# Visual behavior proposal: requirement and evidence ledger

Baseline audit: 10 September 2026. Application revision `dc41aa17ce83999bb56efed1f92ae8842eda70ec`. This ledger traces the complete [proposal](proposal.md); it does not turn its catalog into a smaller task. The 25 trigger families are a catalog and roadmap, the eight named scenes are proposed experiments, and the four increments define their intended implementation order. Later branches remain explicit requirements for their respective claims, even when they are not prerequisites for the first increment.

The baseline receipts below remain an immutable pre-implementation snapshot. Current updates are recorded separately and in the relevant rows. No new motor scenario or neural/body bridge is validated yet. Existing tests establish a reusable foundation without fulfilling a new behavior requirement.

Status vocabulary:

- **Foundation:** relevant code exists, but the proposed feature or scientific result does not.
- **Pending:** the proposed feature, readout, or experiment is absent in the audited revision.
- **Later branch:** additional input, neural module, or physical capability is required; it remains on the roadmap.
- **Prior gate failed:** a previous candidate has retained negative evidence. Its gate is not reset by making the option visible in the app.
- **Validated implementation / validated benefit:** reserve these separate statuses for functional acceptance and successful preregistered physical comparison, respectively. Neither is assigned to a new proposal item by this baseline audit.

## Practical next validation path

1. **Retain offline evidence first.** Extend the full-model export/readout around C3 with a bounded movie set and immutable source/model receipt. Keep stimulus generation separate from the decoder. Use disjoint calibration and held-out manifests; save raw/signed map samples, not just aggregate peak charts. Existing Node oracle tests provide a regression check while the new tests address spatial meaning.
2. **Use the actual body/rendering harness for physical claims.** C10's embodied harness instantiates `Experiment` and `LabArena`, captures renderer-generated eyes, and advances actual policy/BAM/MuJoCo. Reuse that integration pattern, not a mocked plant. Observe `needsFrames()` rather than silently forcing an unrecorded cadence. Ground-truth target/pose information is allowed in scoring and stimulus generation, not candidate input. Freeze exact served modules and loaded decoder hashes with a new run name; retain interrupted/incomplete runs.
3. **Separate source and timeline checks from success metrics.** The temporal server/source guard already rejects missing/stale receipts and duplicate/incomplete trial collections. Preserve that discipline in the new study. Record delivered frame time, model interval, command issue time and actual body response separately; use both a retinal-sequence matched control and a closed-loop physical comparison where appropriate.
4. **Use current UI entry helpers.** `mac/Tests/setup-helpers.js` enters the launch/gallery, opens a scenario, validates every wizard step and waits for worker state. `scenario-audit.js` checks live commands, actual displacement, open-ended scenes and prop edits. New browser checks should follow the same current visible flow rather than directly mutating hidden state.

Use realistic cancelable keyboard events and await the acknowledged worker pause/run state. Native DOM geometry and synthetic camera tests are useful, but do not replace actual-browser visual review or real-camera transfer trials.
